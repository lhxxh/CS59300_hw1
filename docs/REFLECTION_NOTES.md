# Coding agent 反思素材

这份文件记录当前开发过程中能够核实的事实，以及作业要求的反思问题。它不是替你编造的个人经历，也不是最终报告。

## 当前开发事实

- 起始目录只有 `hw1.pdf` 和一个 Python 3.14 的 `.venv`；没有现成应用代码。
- 使用 Codex 阅读作业要求，选择轻量的 Flask、SQLite、原生网页和 pypdf 架构。
- 保留原环境，建立 Python 3.13 的 `.venv-app`，使用 uv 安装依赖。实际解析、准备和安装共不到一秒；原始安装缓慢的原因未被完全确定。
- macOS 命令沙箱导致 uv 初始化和监听 localhost 失败；通过正常的权限审批后成功运行。用户也询问了如何减少反复审批。
- 首次用真实 *Attention Is All You Need* PDF 验证时，作者列表为空，摘要还混入了脚注。原因包括 `∗` 等脚注标记没有清理、Unicode 姓名匹配范围太窄、摘要结束规则不足。
- 随后修正了作者标记清理、Unicode 大写判断、作者区块长度及摘要边界，并复查真实 PDF：正确得到标题、8 位作者、2017 年、摘要和15页正文。
- 添加了针对实际 PDF 解析问题的回归检查。加入 Azure Responses 适配后，核心流程共10个离线检查通过；真实 arXiv、Crossref 和 PDF 下载也已验证。
- 应用要求正文存在后才能分析，长论文按段读取，问答保留来源段落，并明确处理模型 key 缺失、配额/认证失败等情况。
- 初始没有检测到配置好的应用模型 key；用户随后提供 Azure Responses 接口和部署名称 `gpt-5.4-nano`。因此添加了与 Chat Completions 不同的认证及输出解析，实际验证了中文全文总结、论文数据集问答和第7页原文核对。凭据只保存在被忽略的本地 `.env` 中。
- 离线检查在 HTTP 边界模拟返回，不能单独证明真实模型质量；后续真实模型验证覆盖了这篇示例论文，仍需对其他论文和问题检查答案。

## 最终报告要回答的问题

1. 使用了哪个 coding agent？你在哪些开发阶段使用它，给了哪些指令？
2. 它在哪些部分最有帮助？举你实际检查过的架构、代码或调试案例。
3. 哪些输出不正确、不完整或不满意？说明错误如何出现、如何发现、如何修改，并配真实截图。
4. 你实际检查、修改、调试了多少代码？你是否理解前后端、数据库、PDF 解析和模型请求的主要关系？
5. 学到了怎样提出约束、验收结果和控制 agent 的权限？下次会怎样改进你的指令？

完成报告前，还可以自己做一次端到端演示，记录模型是否遗漏信息、引用是否准确、复杂 PDF 的处理是否符合预期，以及你如何引导后续修正。
